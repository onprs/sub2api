# 模型与映射

## 模型名从哪里取得

优先级如下：

1. [渠道监控](https://cdn.api.onprs.top/monitor)中显示的提供商和模型。
2. 客户端使用 Key 请求 `GET /v1/models` 或 Google `GET /v1beta/models`。
3. 控制台“使用 Key”生成的客户端模型配置。

Key 可用分组以创建 Key 时页面可选项为准。不要从旧截图、聊天记录或第三方模型列表复制。

## 客户端模型与上游模型

客户端发送的是“请求模型”。服务端可能依次应用渠道映射、账号映射和平台规则，得到“上游模型”。用量页面会尽量同时显示两者。

这类映射用于：

- 给多个上游提供稳定的用户模型名。
- 把客户端别名映射到当前可用版本。
- 限制特定分组只看到允许的模型。
- 在兼容协议之间选择可用执行路径。

不要依赖某个别名永远映射到同一厂商版本；需要精确能力时查看实时渠道说明。

## 模型列表的边界

`GET /v1/models` 成功只说明 Key、分组和模型发现可用。生成仍可能因为余额、订阅窗口、上游容量或特定能力失败。

Google 模型列表使用 `models/{id}` 形态；URL 生成时通常使用不带 `models/` 前缀的模型 ID。SDK 会按自身规范处理。

## “模型不支持”自查

1. 确认 Key 所属分组与目标平台一致。
2. 打开渠道监控，复制精确模型名，检查大小写、点和连字符。
3. 确认协议路径正确，而不是把 Messages 请求发到 Chat 路径。
4. 暂时删除图片、工具、结构化输出和采样参数，做纯文本最小请求。
5. 检查用量和错误正文中的 requested/upstream model。
6. 换用该分组模型列表中的另一个基础文本模型，区分模型问题与全局问题。

出现 `no available ... accounts supporting model` 时，通常是当前没有满足模型、平台和渠道限制的可调度账号；保留请求 ID 后重试或联系支持，不要高频循环请求。
