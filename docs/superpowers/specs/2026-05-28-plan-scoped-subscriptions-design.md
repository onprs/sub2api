# 套餐维度独立订阅设计

## 目标

允许多个绑定到同一个分组的订阅套餐，在用户侧表现为相互独立的套餐权益，同时保留现有按分组进行账号池路由和模型访问控制的机制。

目标产品行为：

- 用户再次购买同一个套餐时，续期这条套餐权益。
- 用户购买同一分组下的不同套餐时，创建另一条独立套餐权益。
- API 请求仍然按分组路由到同一组账号池。
- 用量只扣一条匹配套餐权益；优先扣“最早过期且额度足够”的套餐权益。

## 当前行为

当前订阅模型把 `group_id` 当作用户订阅身份：

- `user_subscriptions` 对有效记录有 `(user_id, group_id)` 唯一约束。
- `AssignOrExtendSubscription` 按 `user_id + group_id` 查找已有订阅。
- 用户购买同一分组下任何套餐，都会续期同一条订阅记录。
- 购买页只要发现用户已有该分组的有效订阅，就把同分组所有套餐按钮都显示为“续费”。

这个模型适合“一个分组就是一个订阅”的场景，但不适合现在的目标：即使多个套餐共享同一个分组，它们也要作为独立套餐包存在。

## 目标模型

对套餐购买产生的订阅权益，新的订阅身份是：

```text
user_id + group_id + plan_id
```

对没有套餐来源的旧订阅、管理员手动订阅、旧兑换码订阅，仍然保持原来的分组维度：

```text
user_id + group_id + NULL plan_id
```

因此系统会同时支持两类权益：

- 套餐权益：按套餐独立。
- 旧版/手动/分组权益：按分组独立，保持兼容。

## 购买语义

支付订单完成时：

1. 读取订单中的 `plan_id`、`subscription_group_id`、有效天数和套餐额度快照。
2. 如果订单有 `plan_id`：
   - 查找 `user_id + group_id + plan_id` 对应的未删除订阅。
   - 如果找到，续期这条套餐权益。
   - 如果没找到，创建一条新的套餐权益。
3. 如果订单没有 `plan_id`：
   - 走旧逻辑：查找 `user_id + group_id + plan_id IS NULL` 对应的订阅并续期或创建。

例如：

```text
用户已有 Codex-Plus-1
再买 Codex-Plus-1
=> 续期 Codex-Plus-1 这条权益
```

```text
用户已有 Codex-Plus-1
再买 Codex-Plus-2
=> 新增 Codex-Plus-2 这条权益
```

两条权益可以绑定同一个分组，但 `plan_id` 不同，所以可以并存。

## 兑换码语义

由套餐生成的兑换码，应和支付订单使用同一套订阅身份规则：

- 套餐兑换码：按 `user_id + group_id + plan_id` 续期或创建。
- 旧版分组兑换码：按 `user_id + group_id + plan_id IS NULL` 续期或创建。

套餐兑换码已经携带套餐额度快照；还需要确保兑换时能把 `plan_id` 写入用户订阅权益。

兑换码仍然是单次使用，且“标记已使用”和“发放权益”保持事务原子性。用户可以用多个不同套餐的兑换码获得同一分组下的多条独立套餐权益。

## 用量扣减语义

当某次 API 请求使用某个分组时，计费路径应查找所有符合条件的订阅权益：

```text
user_id = 当前用户
group_id = API Key 绑定分组
status = active
expires_at > 当前时间
deleted_at IS NULL
```

然后按以下规则处理：

1. 对候选订阅刷新或重置需要更新的额度窗口。
2. 按 `expires_at ASC` 排序；过期时间相同则按 `id ASC` 排序。
3. 逐条检查该请求成本是否满足所有已配置的额度窗口：
   - `nil` 表示该窗口不限额。
   - `0` 表示该窗口不可用。
   - 正数表示 `当前已用 + 本次成本 <= 限额`。
4. 选择第一条能承担本次成本的订阅权益。
5. 只扣这一条订阅权益的 5h、7d、30d 等用量。
6. usage/billing 记录绑定被实际扣费的 `subscription_id`。
7. 如果所有候选权益都无法承担本次成本，则拒绝请求，沿用现有额度不足/余额不足错误风格。

这保证套餐之间的滚动额度不会被合并成一个大池子，也避免不同购买时间和不同过期时间的套餐账务混在一起。

第一版不做跨套餐拆分扣费。也就是说，一笔 API 请求不会同时扣多条套餐权益。如果最早过期的套餐剩余额度不足以支付完整请求，系统会跳过它并尝试下一条可用套餐。因此可能存在小额剩余额度无法继续使用，并随套餐过期失效的情况。这个取舍用于保持单次请求、usage 记录和订阅扣费关系清晰。

## 用量示例

用户同一分组下有两条有效套餐权益：

```text
套餐 A：3 天后过期，5h 剩余额度 $1
套餐 B：7 天后过期，5h 剩余额度 $20
```

如果某次请求成本是 `$2`：

```text
先检查套餐 A，因为它最早过期
套餐 A 的 5h 剩余额度不够
继续检查套餐 B
套餐 B 额度足够
=> 本次请求扣套餐 B
```

如果某次请求成本是 `$0.5`：

```text
套餐 A 足够
=> 本次请求扣套餐 A
```

如果套餐 A 只剩 `$0.03`，而后续请求通常都超过 `$0.03`，这部分小额尾巴可能无法被继续消耗，并在套餐 A 过期时失效。系统不会把一次 `$0.10` 的请求拆成套餐 A 扣 `$0.03`、套餐 B 扣 `$0.07`。

## 前端行为

套餐卡片按钮应按套餐判断，而不是只按分组判断：

- 用户已有同 `plan_id` 的有效权益：显示“续费”。
- 用户只有同分组其他套餐权益：显示“订阅”或“购买此套餐”。
- 用户没有该分组任何权益：显示“订阅”。

当前订阅区域需要能显示同一分组下的多条套餐权益。每条记录应尽量展示：

- 套餐名称，若有。
- 分组名称。
- 5h、7d、30d 等额度。
- 剩余天数。
- 状态。

这样用户能区分自己持有的是 `Codex-Plus-1`、`Codex-Plus-2` 还是 `Codex-Plus-4`。

## 管理后台行为

订阅管理页需要允许同一用户、同一分组下出现多条有效订阅记录，只要它们来自不同套餐。

列表中应展示套餐身份，例如 `plan_id` 或套餐名称，否则管理员会看到多条相同用户和相同分组的订阅，难以判断来源。

管理员手动分配订阅时，如果没有指定套餐，仍然创建或续期 `plan_id IS NULL` 的旧版分组订阅。

## 数据模型

给 `user_subscriptions` 增加可空字段：

```text
plan_id BIGINT NULL REFERENCES subscription_plans(id) ON DELETE SET NULL
```

唯一约束调整为两个部分唯一索引：

```text
UNIQUE(user_id, group_id, plan_id)
WHERE deleted_at IS NULL AND plan_id IS NOT NULL
```

以及：

```text
UNIQUE(user_id, group_id)
WHERE deleted_at IS NULL AND plan_id IS NULL
```

这样既允许同一用户同一分组下存在多个不同套餐权益，又保留旧版分组订阅的唯一性。

现有订阅记录迁移后保持 `plan_id = NULL`，继续按旧版分组订阅处理。

## API 返回

用户订阅响应需要暴露 `plan_id`，并在符合现有代码模式的前提下尽量暴露套餐信息，例如 `plan` 或 `plan_name`。

购买页判断按钮文案时，应从：

```text
activeSubscription.group_id === plan.group_id
```

改成：

```text
activeSubscription.plan_id === plan.id
```

如果订阅没有 `plan_id`，它只代表旧版分组订阅，不应让同分组所有套餐都显示“续费”。

## 兼容规则

已有用户的旧版分组订阅必须继续可用。

旧版分组订阅和新的套餐订阅可以在同一用户、同一分组下并存。用量扣减时它们都作为候选权益，统一按“最早过期且额度足够”规则处理。

这允许管理员手动发放一条分组订阅，同时用户也购买某个套餐权益。

## 错误处理

- 如果套餐订单引用的套餐后续被下架或删除，履约时应优先使用订单中的套餐快照和已保存的 `plan_id`，不应仅因为套餐不再售卖就失败。
- 如果订单引用的分组已经停用或删除，保持现有履约失败行为。
- 如果没有任何有效权益能承担本次请求成本，返回现有额度不足/余额不足错误。
- 如果并发履约导致唯一约束冲突，应重新读取对应的 `user_id + group_id + plan_id` 权益，然后执行续期。

## 测试策略

后端测试：

- 同一套餐重复购买只续期一条记录。
- 同一分组下不同套餐购买会生成两条独立记录。
- 旧版分组订阅仍然续期 `plan_id IS NULL` 记录。
- 用量扣减会跳过最早过期但额度不足的权益，并扣下一条可用权益。
- 用量扣减会优先扣最早过期且额度足够的权益。
- 兑换两个同分组不同套餐码会生成两条独立权益。
- 兑换同一套餐码对应的同套餐权益时走续期逻辑。

前端测试：

- 只有同 `plan_id` 的有效订阅时，套餐卡片显示“续费”。
- 用户只有同分组其他套餐时，该套餐卡片显示“订阅”。
- 当前订阅列表能显示同一分组下的多条套餐权益，并能展示套餐名称。

## 部署说明

这次改动需要数据库迁移。部署时应继续使用现有安全流程：

1. 备份数据库。
2. 部署包含新迁移和新代码的二进制。
3. 启动服务，让迁移自动执行。
4. 验证购买页、当前订阅列表、订阅套餐支付和 API 用量扣减。

## 回滚风险

这次回滚比普通功能更敏感，因为旧代码假设一个用户在同一分组下最多只有一条有效订阅。

如果新版本上线后已经产生同用户同分组多条套餐权益，再回滚旧代码，旧代码可能无法正确处理这些数据。

安全回滚方式：

- 如果还没有用户生成多套餐权益，可以直接回滚二进制。
- 如果已经生成多套餐权益，应先暂停购买和兑换，再人工合并、删除或软删除同分组重复权益，确保每个用户每个分组只剩一条有效订阅，然后再回滚旧代码。
